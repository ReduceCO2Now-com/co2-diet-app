<objective>
Build the Flutter-side auth UI: one combined sign-in/create-account screen (social buttons, honesty note, email/password fields, Account Mode consent checkbox) and the post-signup "Check your email" screen, per every locked layout/copy/behavior decision in 07-CONTEXT.md's "Auth Screens & Sign-up/Login Flow" section.

Purpose: this is the only screen Local Mode users ever see if they choose to explore Account Mode -- every decision here (equal Apple/Google prominence, no persuasive copy beyond the honesty note, brand-exact social buttons) protects the project's non-manipulative, privacy-first design principle at the one point where a backend account genuinely gets created.

Technical note (resolves an internal tension between 07-CONTEXT.md's literal UI description and AUTH-10's PKCE mandate): AUTH-10 requires Authorization Code + PKCE via the system browser for every credential exchange -- a hand-rolled in-app password submission to Keycloak's token endpoint would be a Resource-Owner-Password-Credentials grant, which is not PKCE and is explicitly listed as an anti-pattern in 07-RESEARCH.md ("Using an embedded WebView... instead of the system browser"). This plan keeps 07-CONTEXT.md's visible email/password fields (autofill hints, min-8-char pre-check, show/hide toggle) exactly as specified, but their role is: (a) the email value is passed as `login_hint` to prefill Keycloak's hosted page, and (b) the password field exists purely to let the OS password manager (iCloud Keychain / Google Password Manager) prime a save-password prompt via `AutofillGroup`/`TextInput.finishAutofillContext`, so the same credential store can autofill inside the system browser too -- directly honoring the PRD's "use existing password managers if possible" intent (07-CONTEXT.md Specific Ideas) without violating AUTH-10. The actual credential verification and any Keycloak-side lockout error happen inside the system browser's own hosted page, which the app cannot intercept mid-session; this is flagged as a coordination point for real-device verification once Tomris's realm exists (07-VALIDATION.md's Manual-Only Verifications table already defers that).

Output: `AuthScreen`, `CheckEmailScreen`, `AppleSignInButton`, `GoogleSignInButton`, and a green, unskipped `auth_screen_test.dart`.
</objective>
