<blockers>

None blocking the start of execution. Two things to carry forward as
awareness, not blockers:

- **Non-blocking observation from the final plan-checker pass:**
  `AuthNotifier.deleteAccount()` (07-03) sends the current access token as a
  Bearer header without an explicit null-guard. `AuthState.authenticated`
  can legitimately have a `null` `accessToken` during the optimistic-restore
  window (cold start before silent refresh resolves, or extended offline
  period under the locked "network failure ≠ logout" behavior).
  `AccountSection` (07-06) renders "Delete account" whenever authenticated
  regardless of token nullity — worst case is a failed request surfaced via
  the existing inline-error path (no data loss, no security exposure), not a
  blocker, but worth a one-line guard during execution review.
- **External dependency, not a blocker for building:** real device testing of
  Apple/Google sign-in, full email-verification flow, and actual account
  deletion all require Tomris to stand up a live Keycloak realm with
  Apple/Google IdP config — none of that exists yet per the backend repo
  scan. The plans are built to be fully constructible and unit/widget-testable
  against mocks without it; only the Manual-Only Verifications are blocked.
</blockers>
