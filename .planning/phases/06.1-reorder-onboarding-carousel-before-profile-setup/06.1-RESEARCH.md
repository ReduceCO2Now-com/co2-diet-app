## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Onboarding-Completion Trigger
- `OnboardingGateNotifier.completeOnboarding()`'s call site **moves from the Carousel to Profile Setup** — Profile Setup is now the last onboarding step, so it owns flipping `hasCompletedOnboarding`.
- The Carousel becomes a **pure pass-through**: both its exit buttons navigate to `/profile` and do **not** call `completeOnboarding()`.
- This preserves the 06-10 bug fix intact: the bottom nav (`AppShell`, keyed off `onboardingGateProvider`) stays hidden through **both** the Carousel and Profile Setup, so there's still no shortcut to bypass Profile Setup via the nav bar. Flipping the trigger at Carousel-exit instead (i.e., leaving it where it is today) was explicitly rejected — it would reintroduce that exact bug.

#### Route Guard
- **No changes to the redirect guard's `onboardingOnlyRoutes` allowlist** (`lib/core/router/app_router.dart`). `/profile` is already deliberately excluded from that list (shared pre-/post-onboarding via `AppShell`, per existing code comment) — only the `completeOnboarding()` call site is moving, not any route's membership in the allowlist.
- Code comments in `app_router.dart` and `AppShell` that describe the old flow order ("Profile Setup → Carousel") need updating to reflect the new order — mechanical, not a routing-logic change.

#### Screen CTAs & Copy
- **Carousel top-right "Skip intro" button:** label unchanged (it describes skipping the slides, not a destination) — destination changes to `/profile`, no `completeOnboarding()` call.
- **Carousel last-slide button:** relabel from `"Go to Dashboard"` to **`"Set Up Profile"`** — destination `/profile`, no `completeOnboarding()` call. (Considered keeping "Go to Dashboard" unchanged for minimal copy churn; rejected as inaccurate now that it doesn't go to the Dashboard.)
- **Profile Setup's forward button:** relabel from `"Continue"` to **`"Go to Dashboard"`** — now the terminal onboarding action; calls `completeOnboarding()` then `context.go('/dashboard')`. Mirrors the exact label the old last step (Carousel) used, keeping the "last step says Go to Dashboard" convention intact.

#### Skip Affordance
- **No new "Skip for now" link added to Profile Setup.** Its fields are already optional and auto-save (06-CONTEXT.md's "no blocking validation" principle) — tapping the forward button with zero fields filled already functions as the skip path. ### Pattern 1: Safe async trigger-then-navigate with mounted guard

**What:** The exact pattern already used by `OnboardingCarouselScreen._finishOnboarding()` — `await` a Riverpod notifier method, check `mounted` before touching `BuildContext` again, then navigate. This is the pattern `ProfileScreen`'s new terminal button handler must replicate, since it's now the one doing the `await completeOnboarding()` + `context.go(...)` sequence that used to live in the Carousel.

**When to use:** Any `onPressed` handler that awaits an async Riverpod call and then calls `context.go(...)` — required whenever a widget can be unmounted mid-await (e.g., user backgrounds the app, or a route change interrupts).

**Example:**
```dart
// Source: lib/features/onboarding/screens/onboarding_carousel_screen.dart:74-77 (existing pattern, being relocated)
Future<void> _finishOnboarding() async {
  await ref.read(onboardingGateProvider.notifier).completeOnboarding();
  if (mounted) context.go('/dashboard');
}
```
`ProfileScreen`'s `_ProfileScreenState` is already a `ConsumerStatefulWidget` (confirmed — `class _ProfileScreenState extends ConsumerState<ProfileScreen>`, line 33), so it already has a `mounted` getter available; no widget-type change is needed to adopt this pattern in `profile_screen.dart`.

### Anti-Patterns to Avoid
- **Firing `completeOnboarding()` without a `mounted` check before the follow-up `context.go(...)`:** this exact bug was found and fixed in Phase 6 (see `onboarding_gate_provider.dart` lines 19-25 — `UnmountedRefException` swallowed the subsequent navigation). Do not reintroduce it in `ProfileScreen`.
- **Changing route declaration order in `app_router.dart`'s `routes: [...]` list to "match" the new flow order:** `go_router`'s `GoRoute`/`StatefulShellRoute` entries are independent path-matched routes, not a sequential flow definition — declaration order has no runtime effect here. Confirmed by reading the full `routes:` list (lines 189-338): order is currently grouped by feature area, not flow sequence, and Profile/Dashboard/Settings already live inside the `StatefulShellRoute` regardless of when they're reached in the user journey. No reorder needed.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Detecting whether a widget is still mounted before post-await `BuildContext` use | A custom `_disposed` flag or try/catch around `context.go` | `State.mounted` (already the established pattern in this file) | Framework-provided, already the codebase convention (see `onboarding_carousel_screen.dart`, `profile_screen.dart`'s own `if (!mounted) return;` at line 74) |
| Re-deriving "is onboarding done" state in the reordered screens | A new local flag/provider | Existing `onboardingGateProvider` (`ref.watch`/`ref.read`) | Single source of truth already exists and is already `keepAlive: true`; do not introduce a second signal |

**Key insight:** This phase's entire "don't hand-roll" surface is about *not* touching things that don't need touching — `OnboardingGateNotifier`, the redirect guard, and `AppShell`'s bottom-nav logic are all correct as-is and must be left alone except for comment text.

## Common Pitfalls

### Pitfall 1: `_finishOnboarding()` method name becomes misleading after the edit
**What goes wrong:** `OnboardingCarouselScreen._finishOnboarding()` is currently named for what it does today (finish onboarding + navigate). After this phase, it will no longer call `completeOnboarding()` — it becomes a plain pass-through navigator. Leaving the method named `_finishOnboarding` would misdescribe its new behavior to the next reader.
**Why it happens:** Reorders that "just change destinations" are easy to under-scope as a one-line diff when the method's identity also needs updating.
**How to avoid:** Rename the method (e.g., `_goToProfile` or `_exitCarousel`) as part of the same edit, and update its call sites (both the "Skip intro" `onPressed` and the last-slide `onPressed`).
**Warning signs:** Grep for `_finishOnboarding` after the change — any surviving reference (including in comments) is a signal the rename was incomplete.

### Pitfall 2: Stale test name/comment describing the old trigger site (found, not hypothetical)
**What goes wrong:** `test/features/onboarding/onboarding_gate_test.dart` (lines 236-274) has a test literally named `'calling completeOnboarding() mid-session (as the Carousel does) then navigating to /dashboard produces no redirect back to /splash'`, with an in-body comment `// Mirrors OnboardingCarouselScreen._finishOnboarding(): call the notifier live`. The test's actual assertions (call `completeOnboarding()` directly on the provider, then navigate to `/dashboard`, expect no redirect) will **still pass** after the reorder — they test the redirect guard's behavior generically, not literally which screen calls the method. But the test's name and comment will now describe a call site that no longer exists.
**Why it happens:** Widget/unit tests that call a notifier method directly (rather than through the real screen's button) don't break when the screen's call site moves — they silently go stale in *description* while staying green in *execution*. This is easy to miss because CI won't flag it.
**How to avoid:** As part of this phase, rename the test and rewrite its comment to describe the new trigger site (Profile Setup), even though the assertion logic itself needs zero changes. This was explicitly flagged in CONTEXT.md's `Claude's Discretion` as "existing test file updates needed ... which files, exact assertions" — this is the answer: this one file, comment/name-only, no assertion changes.
**Warning signs:** Searching for `"as the Carousel does"` or `"Mirrors OnboardingCarouselScreen._finishOnboarding"` in the test suite post-change will surface this exact staleness.

### Pitfall 3: Assuming the redirect guard needs `/profile` re-added to `onboardingOnlyRoutes`
**What goes wrong:** It's tempting to think "Profile Setup is now the *last* pre-completion screen, so surely it needs to move into the onboarding-only allowlist (with a bounce-away-once-complete rule), mirroring how `/onboarding-carousel` is currently treated."
**Why it happens:** The pre-reorder flow's last screen (Carousel) IS in `onboardingOnlyRoutes` (redirects a completed user away from it back to `/dashboard`). Surface-level pattern-matching suggests the new last screen should get the same treatment.
**How to avoid:** Don't do this. CONTEXT.md is explicit and was independently re-verified against the live router code: `/profile` is *deliberately* excluded from `onboardingOnlyRoutes` because it's a genuinely dual-purpose route — the same screen instance serves both the onboarding-only Profile Setup step (pre-`completeOnboarding()`) AND the permanent post-onboarding Profile bottom-nav tab. A completed user must still be able to visit `/profile` normally (confirmed by the router's own comment at line 178: `// Deliberately does NOT include '/profile' here — a completed user must still be able to visit the Profile bottom-nav tab normally.`). This is unchanged by the reorder and must stay unchanged.
**Warning signs:** If a plan/task proposes adding `/profile` to `onboardingOnlyRoutes` or `onboardingOnlyRoutes`-equivalent logic, that's a regression of existing, tested, correct behavior — reject it.

### Pitfall 4: Forgetting the `!hasOnboarded` conditional button still needs to work correctly for BOTH pre- and post-onboarding profile visits
**What goes wrong:** `ProfileScreen`'s forward button is already conditionally rendered (`if (!hasOnboarded) ...`, line 132) — it only shows during the onboarding-flow visit to `/profile`, not on the permanent post-onboarding Profile tab. This conditional rendering logic itself does not need to change (it already correctly distinguishes the two visit contexts via the same `onboardingGateProvider` watch used elsewhere) — only the button's label, destination, and side-effect (now firing `completeOnboarding()`) change.
**Why it happens:** It's easy to over-scope the edit and start restructuring the `if (!hasOnboarded)` block itself when only its *contents* (the `FilledButton`'s `onPressed`/`child`) need to change.
**How to avoid:** Keep the `if (!hasOnboarded) ...` gate exactly as-is; only edit the `FilledButton`'s `onPressed` callback body and its `Text` label inside it.
**Warning signs:** A diff touching `hasOnboarded` itself, or the `if` condition, when the task was scoped as "change the button's action" — that's scope creep into already-correct code.
