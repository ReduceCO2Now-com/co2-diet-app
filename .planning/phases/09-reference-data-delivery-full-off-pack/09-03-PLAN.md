<objective>
Build the three independent data-layer primitives Plan 09-04's repository orchestrates: the manifest HTTP client, the atomic on-disk swap mechanism (extending first_launch_extractor.dart's pattern to a live, already-open AppDatabase connection -- including the gzip-decompression step that pattern already performs for the bundled seed, since the downloaded full pack ships compressed the same way), and a testable wrapper around background_downloader that expresses CONTEXT.md's resumable/Wi-Fi-gated/cancel-vs-interruption download rules natively instead of hand-rolling them.

Purpose: 09-RESEARCH.md's Don't Hand-Roll table and Pitfall 2/4/5 all point at the same class of risk -- treating background_downloader as a black box called ad hoc from the repository, re-deriving Range-header resume logic by hand, or forgetting that `tools/build_reference_pack_release.py` (Plan 09-07) ships the full pack exactly the way `tools/ingest_off.py` already ships the bundled seed: gzip-compressed. `first_launch_extractor.dart` already decompresses before ever writing a usable `.sqlite` file -- this plan's extractor must do the same for the downloaded artifact, or `ATTACH DATABASE` will be pointed at a `.gz` file and fail outright. Isolating the native-plugin surface behind one DownloadManager class, and the live-swap-plus-decompress surface behind one ReferencePackExtractor class, means Plan 09-04's repository composes pure, already-tested primitives instead of re-deriving platform-channel or archive-format behavior itself. Because the DETACH/decompress/rename/ATTACH ordering is the exact fix that closed this phase's iteration-1 blocker, it gets its own real-fixture automated test in this plan rather than relying solely on `flutter analyze`, a mocked repository test one plan later, or a manual real-device checkpoint four plans later (Plan 09-08) to catch a regression.

Output: ReferencePackApiClient, ReferencePackExtractor (with a dedicated real-fixture test proving decompress-before-ATTACH ordering), DownloadManager, a small FoodCatalogDao.countProducts() addition (needed for the product-count comparison UI, 09-CONTEXT.md's locked "50,000 products (starter pack)" requirement), and unit tests for the three primitives whose logic is directly testable without a real platform channel (ReferencePackApiClient.fetchManifest(), ReferencePackExtractor.swapIn/revertToSeed, DownloadManager's filename-sanitization/status-mapping helpers).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| CDN pack/delta binary content | Untrusted bytes flow from a network response into on-disk files before verification (checksum happens one plan later, in the orchestrating repository) |
| Gzip decompression of the downloaded pack | The decompressed byte stream is only ever produced from a file whose checksum has already been verified by the caller (Plan 09-04) -- this plan's extractor never decompresses an unverified file |
| Live SQLite ATTACH/DETACH while AppDatabase is open | A concurrency boundary, not a data-trust boundary -- getting this wrong corrupts local reads, it does not leak data |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-03-01 | Tampering | DownloadManager filename construction | mitigate | Every on-disk filename is built by DownloadManager's own sanitizedFilename() helper from a sanitized version string it owns, never taken verbatim from a manifest/server-supplied string (extends T-02-03-02); covered by download_manager_test.dart |
| T-09-03-02 | Tampering | ReferencePackExtractor.swapIn (unverified file swapped in / decompressed) | accept (deferred) | Checksum verification happens in the calling repository (Plan 09-04) before swapIn is ever invoked -- this plan's extractor trusts its input by design, including the decompression step, since verification is a separate, already-planned concern one layer up |
