<objective>
Build DeltaApplier (the single highest-value new behavior this phase needs, per 09-RESEARCH.md) and ReferencePackRepository -- the orchestration layer that composes every Plan 09-02/09-03 primitive (ChecksumVerifier, DiskSpaceChecker, ReferencePackApiClient, DownloadManager, ReferencePackExtractor, ReferencePackVersionStore) into the documented preflight -> manifest -> download -> verify -> swap sequence from 09-RESEARCH.md's architecture diagram -- and, critically, wires DeltaApplier itself into that same repository's delta-download completion path, since Plan 09-06's automatic weekly/monthly refresh has nothing else to call.

Purpose: products_fts is declared content='products' with no sync trigger (grep-verified against tools/ingest_off.py's DDL) -- any code that writes to products without also rebuilding products_fts leaves search silently stale, which is exactly the kind of bug that would only surface as "the download said it worked but I can't find the new products." Isolating this in one DeltaApplier class, proven by a real SQLite integration test, closes that gap before any UI can trigger it -- but a correct, isolated DeltaApplier is worthless to this phase's "incremental delta refresh" success criterion unless something in the actual download-completion flow calls it, so this plan also wires ReferencePackRepository's startDeltaDownload completion path to checksum-verify the delta file and hand it to DeltaApplier.apply, not just to declare the interface method that a later plan happens to call. Separately, CONTEXT.md's disk-space preflight decision only holds if the two numbers fed into it are genuinely different: the manifest's advertised size describes the compressed download (Plan 09-07's build script gzips the full pack, exactly like the bundled seed's existing tools/ingest_off.py convention), while the file that ends up installed on disk is the decompressed .sqlite -- these must never be conflated into a single value.

Output: DeltaApplier (integration-tested against a real SQLite fixture), ReferencePackRepository (with DeltaApplier wired into its delta-download completion path, and an honest, documented compressed-vs-decompressed disk-space estimate), and reference_pack_providers.dart -- everything Plan 09-05's UI layer and Plan 09-06's automatic refresh path need is now a stable, fully-tested contract.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Downloaded pack/delta file -> live database swap | The point where an untrusted network artifact becomes trusted local data -- checksum verification (against the still-compressed download for full packs, against the downloaded file as-is for deltas) is the gate |
| Delta artifact -> products/products_fts | A structured-but-untrusted-until-checksummed SQL payload applied via ATTACH, not parsed field-by-field |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-04-01 | Tampering | ReferencePackRepository's download-completion path (full AND delta) | mitigate | Mandatory ChecksumVerifier.verify() gate (against the still-compressed download for full packs, against the downloaded delta file for deltas) before ReferencePackExtractor.swapIn or DeltaApplier.apply is ever called on a downloaded file |
| T-09-04-02 | Tampering | DeltaApplier's explicit-column INSERT | mitigate | Named-column SELECT (never SELECT *) prevents a column-order mismatch between the delta artifact's schema and off_ref.products from silently corrupting data |
| T-09-04-03 | Information Disclosure | products_fts rebuild after delta apply | accept | products_fts contains only public OFF catalog data (product names/brands), never personal user data -- no confidentiality concern in a full rebuild |
| T-09-04-04 | Denial of Service | checkDiskSpace() underestimating required disk space | mitigate | Decompressed-size estimate uses a deliberately conservative (round-up) compression-ratio constant grounded in this project's own measured bundled-seed ratio, never reuses the compressed download size as a stand-in for the decompressed footprint |
| T-09-04-05 | Tampering | Delta/full download-kind tracking inside ReferencePackRepository | mitigate | The repository's internal in-flight-download-kind field is set only by startFullDownload/startDeltaDownload immediately before enqueuing, and cleared on completion/cancel/failure, so a completion event can never be routed through the wrong completion path (swapIn vs. DeltaApplier.apply) |
