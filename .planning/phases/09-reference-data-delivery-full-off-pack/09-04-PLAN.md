    - Applying a delta whose products_delta table contains a new barcode inserts that row into products AND makes it immediately findable via a products_fts MATCH query on its product_name.
    - Applying a delta whose products_delta table contains a barcode that already exists in products replaces the row (INSERT OR REPLACE semantics) and the updated product_name is what products_fts now matches, not the stale one.
    - Applying a delta whose deleted_barcodes table lists a barcode removes that row from both products and products_fts -- a subsequent MATCH query for its old name returns nothing.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Downloaded pack/delta file -> live database swap | The point where an untrusted network artifact becomes trusted local data -- checksum verification is the gate |
| Delta artifact -> products/products_fts | A structured-but-untrusted-until-checksummed SQL payload applied via ATTACH, not parsed field-by-field |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-04-01 | Tampering | ReferencePackRepository's download-completion path | mitigate | Mandatory ChecksumVerifier.verify() gate before ReferencePackExtractor.swapIn or DeltaApplier.apply is ever called on a downloaded file |
| T-09-04-02 | Tampering | DeltaApplier's explicit-column INSERT | mitigate | Named-column SELECT (never SELECT *) prevents a column-order mismatch between the delta artifact's schema and off_ref.products from silently corrupting data |
| T-09-04-03 | Information Disclosure | products_fts rebuild after delta apply | accept | products_fts contains only public OFF catalog data (product names/brands), never personal user data -- no confidentiality concern in a full rebuild |
</threat_model>
