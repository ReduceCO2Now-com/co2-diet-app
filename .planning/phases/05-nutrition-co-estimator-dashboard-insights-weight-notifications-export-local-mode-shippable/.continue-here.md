- Test 7 (Backup & Restore) started: walked through

- **Root cause found:** `_readCategoryRows()` (backup_export_service.dart:442-468)
  calls `row.toJson(serializer: _serializer)` on the *raw Drift row* for
  every `ExportCategory`, with no field filtering. Every one of the 7
  categories' backing tables (`user_profile_table.dart`,
  `meal_entry_table.dart`, `favorite_table.dart`, `user_food_table.dart`,
  `weight_entry_table.dart`, `co2_settings_table.dart`,
  `notification_prefs_table.dart`) mixes in `SyncSafeTable`
  (`lib/data/local/mixins/sync_safe_table.dart`), which injects 6
  internal sync-machinery columns onto every table: `id` (UUID v7),
  `hlcMillis`, `hlcCounter`, `hlcNodeId` (HLC clock components — Phase-1
  placeholders per `backup_export_service.dart`'s own comments),
  `dirty` (local-changes flag), `deletedAt` (soft-delete tombstone).
  Confirmed via `grep -l "with SyncSafeTable" lib/data/local/tables/*.dart`
  — all 7 export categories' tables are on the list. So this is not a
  Profile-specific bug — it's a shared-helper bug that leaks the same 6
  internal columns into every category's CSV/Excel/JSON export and into
  every backup zip.
- **Fix implemented and committed (`8545e1e`):** checked `_restoreCategory()`
  first and confirmed `applyRestore()`'s `*Row.fromJson()` genuinely needs
  every `SyncSafeTable` column to reconstruct a valid row — so the fix
  had to diverge backup fidelity from human-export fidelity, not apply
  one filter to both. Added `includeInternalFields` param to
  `exportData()` (default `false`), backed by a new
  `_stripInternalFields()` helper keyed off a `_internalFieldNames`
  constant (`id`/`hlcMillis`/`hlcCounter`/`hlcNodeId`/`dirty`/
  `deletedAt`). `createBackup()` now passes `includeInternalFields: true`
  so restore is unaffected. `BackupNotifier.shareExport()` (the actual
  "Export Data"/"Share export" UI path) gets the stripped default
  automatically — no caller-side change needed there.
- Wrote 2 new regression tests in `backup_export_service_test.dart`
  first, confirmed the leak test genuinely failed against pre-fix code
  (`row.containsKey('id')` was `true`), then implemented the fix and
  reverified both pass. Full suite (379 tests) green, `flutter analyze`
  clean on the touched file.
- Wrote up the bug as a `resolved` gap entry in `05-UAT.md`'s Gaps
