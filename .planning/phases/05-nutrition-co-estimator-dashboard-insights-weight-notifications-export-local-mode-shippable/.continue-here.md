**Test 5/6 (meal + weigh-in reminders) -- RESOLVED, THREE stacked root causes found and fixed, user-confirmed firing on real device:**

- **Root cause 1 (commit `025bc55`):** `NotificationService.initialize()` never called `tz_data.initializeTimeZones()`/`tz.setLocalLocation(...)` despite its own doc comment claiming it does -- `tz.local` is a package-global `late` field with no default, so the first read of it threw `LateInitializationError`, uncaught (not a `PlatformException`), silently preventing any scheduling. Reproduced via a widget test isolated from `notification_service_test.dart` (whose `setUpAll` pre-seeds `tz.setLocalLocation`, masking this gap). Fixed by actually calling `tz_data.initializeTimeZones()` + `FlutterTimezone.getLocalTimezone()`.
- User did a genuinely fresh rebuild+restart of that fix and STILL saw nothing fire, and explicitly asked for real device evidence rather than another theory. Ran `integration_test/notification_scheduling_test.dart` (real, non-mocked plugin) on the user's connected Tab S7 FE (`R52RB0FSSAX`), commit `2285c60`: `tz.local` resolved correctly, scheduling succeeded, `pendingNotificationRequests()` showed 3 pending notifications -- but waiting past the scheduled time in real time via `adb` showed the alarm never fired.
- **User independently found a second, sharp, concrete clue:** the app was entirely absent from Settings > Apps > Special access > Alarms & reminders. That page only lists apps that declared `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM`. Investigating led to **root cause 2 (commit `973a9eb`):** `android/app/src/main/AndroidManifest.xml` never declared the `ScheduledNotificationReceiver`/`ScheduledNotificationBootReceiver` that `flutter_local_notifications` (>= v16) requires the CONSUMING app to declare itself (the plugin stopped bundling these in its own manifest). Without the receiver, `AlarmManager` had no registered component to deliver the broadcast to -- confirmed by directly inspecting the actual merged manifest baked into the previously-tested APK (receivers genuinely absent). Added them, rebuilt, confirmed present, then confirmed via `adb shell dumpsys alarm` that `AlarmManager` now holds a validly-targeted alarm.
- Still wasn't firing after ~8 minutes of real-time waiting (checked via `adb shell dumpsys alarm`/`dumpsys notification` directly). Agreed with the user this pointed to **root cause 3:** `AndroidScheduleMode.inexactAllowWhileIdle` is structurally the wrong choice for a time-anchored reminder feature (not a workaround to switch away from -- exact scheduling is the product-correct behavior here). User explicitly approved switching to `exactAllowWhileIdle` + `SCHEDULE_EXACT_ALARM` (commit `973a9eb`), with the SAME just-in-time, clearly-explained permission pattern already used for camera/notification permission (`NotificationService.requestExactAlarmPermissionIfNeeded()`, wired into both `MealReminderSettingsSection`'s and `WeighInReminderSection`'s toggle handlers -- deny reverts the toggle + shows "Open Settings").
