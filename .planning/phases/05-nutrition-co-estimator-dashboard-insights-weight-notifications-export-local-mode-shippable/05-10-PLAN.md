<objective>
Build the two pure-Dart aggregation services every Dashboard/Insights screen reads from: `DailyTotalsCalculator` (NUTR-01/NUTR-02/NUTR-03/NUTR-04, sums calories/protein/carbs/fat/sugar/fiber/salt/co2e across a list of `MealEntry`) and `PersonalCo2MultiplierCalculator` (CO2-02/CO2-03, derives a deterministic personal-consumption multiplier from `Co2Settings`, applied only at the total level).

Purpose: Per the Architectural Responsibility Map, aggregation/ranking logic belongs in a domain/service layer, not inline in widgets — `DailyTotalsCalculator` is the single implementation both the Dashboard (05-11) and Data Analysis screen (05-15) call, so their numbers can never silently diverge. `PersonalCo2MultiplierCalculator` enforces CONTEXT.md's separate-layer invariant by construction: it takes only `Co2Settings` as input and returns a `double` — it has no way to touch a `MealEntry`'s `co2e100gSnapshot` even if a future caller tried.

Known limitation (inherited from Phase 4, not introduced here): only weight-based-unit (`g`/`ml`) entries can be scaled and therefore contribute to any numeric total — `piece`/`cup`/`portion` entries have no gram-equivalent stored at log time, matching `MealEntryRow`/`RecentRow`'s existing "weight-based units only" precedent ([Phase 04-10] decision). This is documented explicitly, not silently dropped.

Output: `DailyTotalsCalculator` and `PersonalCo2MultiplierCalculator`, both zero-I/O pure functions.
</objective>
