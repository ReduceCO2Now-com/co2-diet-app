<objective>
Add every new Drift table Phase 5 needs (`Co2SettingsTable`, `WeightEntryTable`, `WeightSettingsTable`, `NotificationPrefsTable`, `BackupMetadataTable`), add the three missing nutrient-snapshot columns to the existing `MealEntryTable` (RESEARCH.md Pitfall 1: `sugar100gSnapshot`/`fiber100gSnapshot`/`saltSnapshot`, nullable), and bump `AppDatabase.schemaVersion` from 3 to 4 in a single migration step.

Purpose: This is the foundational data layer every other Phase 5 plan depends on. Per the `SyncSafeTable` convention (established Phase 1-4), every new table uses the mixin for Phase 7 sync readiness. Singleton tables (`Co2SettingsTable`, `WeightSettingsTable`, `NotificationPrefsTable`, `BackupMetadataTable`) follow `UserProfileTable`'s exact "one row ever, upsert on PK" pattern rather than inventing a new one.

`MealEntryTable`'s nutrient gap (RESEARCH.md's highest-priority finding) is a hard blocker for NUTR-01 — daily/meal totals cannot include sugar/fiber/sodium for newly-logged entries without these columns existing first. Note this codebase already tracks the "sodium" nutrient as **salt (g)**, matching the EU nutrition-label convention already established by `UserFoodTable.salt`/`UserFood.salt` (Phase 4) — this plan's `saltSnapshot` column is this app's chosen implementation of NUTR-01's "sodium" tracking requirement, not a distinct fourth nutrient. Do not invent a salt-to-sodium unit conversion; treat the two terms as the same field, consistent with every other place in this codebase.

Output: Five new table files, three new `MealEntryTable` columns, an updated migration strategy, and `AppDatabase` registered at schemaVersion 4 with all five tables added to `@DriftDatabase(tables: [...])`.
</objective>
